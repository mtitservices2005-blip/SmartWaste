# Revisión de preparación para MTIT-OS Core

> Datos demo · no producción. Análisis de solo lectura del código en `docs/CURRENT_STATE_AUDIT.md` + verificación SW-020. No modifica código — es la base para decidir el siguiente hito de refactor (a definir, ver sección final). Basado en `CLAUDE.md` (visión MTIT-OS, 2026-07-30): "el objetivo actual no es agregar muchas funcionalidades... es preparar SmartWaste para convertirse en un consumidor del MTIT-OS Core."

## Pregunta guía

Por cada pieza de `shared/` y del esquema de Supabase: ¿esto es responsabilidad exclusiva de SmartWaste (gestión de residuos), o es algo que MTIT-OS Core (Shared/Identity/Municipality/Workflow) va a asumir? Donde la respuesta es "Core", el objetivo no es borrar el código hoy (Core todavía no existe) sino **aislarlo detrás de una interfaz reemplazable**, para no acumular más lógica que después haya que desenredar.

## Lo que esto NO implica

No hay que reescribir `auth-context.js` ni las tablas `profiles`/`memberships`/`municipalities` hoy. MTIT-OS Identity/Municipality Core todavía no existen (per tu documento: "MTIT-OS ya comenzó el desarrollo de su Core" — comenzó, no está disponible para consumir). Reemplazar código funcional por una integración que no existe todavía sería el error opuesto: dejar SmartWaste roto esperando un Core que aún no se puede consumir. Regla 5 y 7 de `CLAUDE.md` (no romper la demo, no introducir deuda técnica evitable) aplican también en esta dirección.

## Recomendación concreta para el siguiente hito de refactor (no ejecutado en esta revisión)

1. **No tocar el esquema de datos todavía.** Cambiarlo ahora, sin un contrato real de Core que consumir, sería adivinar una interfaz que probablemente no va a coincidir con la real.
2. **Sí introducir un seam (punto de sustitución) en el código de aplicación**, sin cambiar comportamiento:
   - Envolver `resolveSupabaseAuthContext()` y `ROLES`/`PERMISSIONS`/`can()` detrás de una interfaz `IdentityProvider` (hoy con una única implementación: la actual, contra `profiles`/`memberships`). Nada más se toca; los call sites (tests, futuro frontend) dependen de la interfaz, no de la implementación.
   - Mismo patrón para tenancy: una interfaz `MunicipalityScope` que hoy delega a `assertSameMunicipality()`/`municipality_id`.
   - Para el ciclo de vida operativo, mantener `shared/operations-adapter.js` como el único punto de entrada (ya lo es) y documentar explícitamente que es el candidato a delegar en `MT Workflow` (`CreateWorkOrder`/`AssignWorkOrder`/...) cuando exista, sin exponer `route_runs`/`vehicle_assignments` fuera de este módulo.
3. **Formalizar `shared/channel-contracts.js` como contrato versionado** (JSON Schema u OpenAPI mínimo) en vez de objetos JS internos — ya señalado en `docs/MTIT_OS_BOUNDARY_REVIEW.md`, se reafirma acá porque es la pieza más cercana a una integración real con Citizen AI.
4. **Antes de construir un sistema de auditoría propio más allá de `audit_events`**, confirmar con el equipo de MTIT-OS si Shared va a proveer esa capacidad — evitar construir dos veces lo mismo.
5. **Aclarar con el equipo de arquitectura la ambigüedad de "sectores"** (tabla propia vs. primitivo compartido de Core) antes de que el modelo de datos de sectores crezca más.

Este listado es la base para decidir un hito futuro (ej. "SW-021: seams de Core-readiness") — no se ejecuta como parte de esta revisión.
